# ADR 0028: String-Backed Bin Rendering Boundary

## Status

Accepted

## Context

hbci4java's `SyntaxBin` accepts two outbound input forms:

- `B...` means the remaining data is already binary content and is rendered as
  `@len@payload`.
- `N...` means the remaining data is a decimal integer and is converted with
  `BigInteger.toByteArray()` before rendering as `@len@payload`.

The Rust port currently models rendered wire data as UTF-8 `String`s. That is
enough for protocol-table loading, most PinTAN text fields, SEPA XML payloads,
and many fixtures, but it cannot losslessly represent arbitrary binary byte
sequences such as `0xff`.

## Decision

Keep the current string-backed protocol renderer for this phase, but move `Bin`
rendering closer to hbci4java:

- keep supporting `B...` as direct binary payload text;
- add `N...` rendering for non-negative decimal integers using Java-like
  big-endian `BigInteger.toByteArray()` bytes;
- reject numeric binary payloads whose generated bytes are not valid UTF-8;
- record full byte-oriented wire rendering as a later protocol boundary change,
  not as an ad hoc lossy conversion.

## Consequences

Outgoing `Bin` rendering now supports simple numeric inputs and real `HNVSD`
length-prefixed blocks without quoting delimiters inside the payload.

This is still not a complete `SyntaxBin` port. Fully arbitrary binary payloads
will require changing the renderer and parser boundary from `String` to bytes or
adding an explicit byte payload type. Until then, rejecting non-UTF-8 numeric
payloads is preferable to silently corrupting FinTS wire data.
